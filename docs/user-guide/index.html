GovLens User Guide

Continuous Azure & Entra governance visibility, plus a reviewed self-service access workflow - grant and revoke Azure roles safely, with least-privilege and an audit trail.

Screenshots in this guide use example data (Example Org, example.com users). Your deployment shows your own tenant.

What is GovLens

GovLens does two jobs for a Microsoft cloud tenant:

  • Governance visibility - a read-only collector regularly pulls your Azure Policy compliance, RBAC role assignments, Entra Conditional Access, and directory-role assignments, and shows them on a dashboard with trends and drift.
  • Reviewed access lifecycle - users request access through a guided wizard; approvers review and set an expiry; a separate worker provisions the grant and auto-revokes it when it expires. Revoking existing access follows the same review flow.

It's designed to be the cheapest, leanest governance option for small-to-mid orgs: one container, your own database, three least-privilege service principals.

ScopeWhere a grant/role applies: tenant-wide (*), a subscription, or a resource group.
ModulesThe background workers: collector (read), remediator (executes revokes), grant (provisions self-service grants). Each is independently toggleable.

Signing in

GovLens uses your organization's identity provider (Entra ID single sign-on by default). Click through the Microsoft sign-in; GovLens reads your name, email, and directory object id from the token. Your in-app roles (user / approver / admin) are resolved from GovLens's own grants - bootstrap admins come from the deployment config.

Tip: the first time you sign in after self-service is enabled, sign out and back in once so your directory object id is captured - it's the target of any grant you request for yourself.

The dashboard

The landing page summarizes tenant governance at a glance: Policy compliance %, Maester pass rate, Conditional Access coverage, and total RBAC assignments - each with the change since the previous run. Below, a compliance trend chart, a drift panel (what access was added/removed between the two most recent runs, with false-removals suppressed when a collector didn't run), and the list of failing controls. Requesting access

Any signed-in user can request access from Request access. It's a four-step wizard that hides Azure's hundreds of raw roles behind plain choices:

  1. Where - pick a subscription, and optionally narrow to a single resource group for tighter, least-privilege access.
  2. How much access - choose a level: Read-only, Contribute, or Admin. Each shows a sensible default role (you can pick a different one from that level), plus the policy: who approves and the maximum duration.
  3. For how long - a duration preset (1 / 7 / 30 days or custom). Where policy allows, an ∞ Unlimited option appears for a no-expiry grant.
  4. Why you need it - a short justification (required). Your request then goes to an approver.

Grants are time-bound by default and provisioned to you (your directory object id). The role appears in Azure automatically once approved, and is revoked automatically when it expires.

The Requests hub

Requests is the shared hub for both grant and revoke workflows. It has three parts:

  • Access requests - grants: pending grant requests awaiting review.
  • Revoke requests: pending revocations awaiting review.
  • History: every decided request (grants and revokes together, tagged by type) with a step-by-step timeline, search, and pagination (20 per page).

Who sees what (visibility matrix): you always see your own requests; a global approver/admin sees everything; a subscription-scoped approver/admin sees requests for their subscription(s).

Reviewing & approving

On a pending grant, an approver sets the expiry (in days) or ticks permanent where the level's policy allows it, adds an optional note, and clicks Approve (or Reject). The requester's proposed duration is shown as a hint. On a pending revoke, the approver simply approves or rejects.

  • Approval is scope-aware: you can only decide requests for scopes you approve.
  • Some levels require a global approver (set per tier). Those requests won't accept a subscription approver's decision.
  • The lifecycle timeline records each step with who and when - Requested → Approved → Granted → Expires for grants, and Requested → Approved → Removed for revokes.

Revoking access

To remove existing access, open a run's detail page, find the role assignment, and click Revoke to mark it. That opens a revoke request in the Requests hub (marking writes only to GovLens's queue - it changes nothing in Azure yet). After an approver approves it, the remediator worker performs the deletion on its next cycle and records the removal time. Protected roles and blocked principal types can't be marked at all.

Marking, approval, and execution are separated by design: the web app never deletes anything - a distinct worker with its own credential does, only for approved requests, behind a safety gate.

Administration

Admins get an Admin page to manage people and policy. From here you grant approver/admin roles (global or per-subscription), maintain the non-revocable role list, set per-principal-type revocation policy, and configure the self-service grant module.

Enabling self-service (the gates)

Self-service grant is off by default and only goes live when a fail-closed checklist is complete:

  1. Capability on - a global admin turns the module on.
  2. Grant SP verified - configure the write-capable service principal and run the readiness probe (confirms it can create role assignments and isn't over-permissioned).
  3. Tier policy acknowledged - review each level's rules.
  4. Catalog - requestable roles are auto-discovered on collection.
  5. Subscription opt-in - each subscription admin opts their subscription in.
  6. Go live - allowed only when every gate above is green.

Levels & tier policy

Roles are auto-classified by their permissions into three tiers, surfaced to users as levels:

LevelTierTypical defaultGoverns
Read-onlylowReaderself-service on, long/uncapped, subscription approver
Contributemediumdata / resource rolesself-service on, capped duration (e.g. 90 days)
AdminprivilegedOwner, User Access Administrator…hidden by default; global approver, short duration

Each tier has four knobs an admin tunes: self-service (requestable?), default and max days, allow permanent, and approver (scoped or global). Anything the classifier can't place lands in privileged - fail-closed.

Guardrails

  • Non-revocable roles - roles that can never be removed through GovLens (e.g. Global Administrator).
  • Principal-type policy - per identity type (User / Group / Service Principal): blocked (never revocable) or global-approval-required.
  • Least-privilege by construction - narrower scopes (resource group over subscription) and shorter durations are always available and encouraged.

How it works

Three background workers run against your database:

  • Collector - read-only SP → pulls governance data → stores a run.
  • Remediator - a roles-only SP with delete → executes approved revokes (and the auto-revocation of expired grants).
  • Grant worker - a roles-only SP with write → provisions approved grants and sweeps expired ones. It re-checks its own permissions each cycle to keep the readiness gate fresh.

The web app only reads from and writes to the request queue; it never touches Azure directly. The queue (the access_requests table) is also the audit trail.

Security model

  • Three separated credentials - read-only, delete-only, write-only - so no single component can both read broadly and change access.
  • Cert or secret - each service principal authenticates with a certificate or a client secret (your choice).
  • Fail-closed everywhere - the grant module won't go live until every gate is green; unknown roles are treated as privileged; a stale SP-verification closes the module.
  • Time-bound by default - grants expire and are auto-revoked; "permanent" is a policy-gated exception.
  • Full audit trail - every request records who asked, who approved, when it was provisioned, and when it expired/was removed.

Deployment

GovLens ships as a single container image driven by one YAML config, against your own Postgres:

docker run -v ./config.yaml:/etc/govlens/config.yaml -p 8080:8080 ghcr.io/automationpi/govlens

The config file holds the database connection string, authentication, the three service principals (each cert or secret), and which modules run. Any value can use ${ENV_VAR} so secrets stay in the environment. See config.example.yaml and docs/DEPLOY.md for the full reference. The database is yours - GovLens creates its own schema on first start and never manages a database.

FAQ

I requested access but nothing happened.

Requests need approval. Check the Requests hub - your request is pending until an approver decides. After approval, the grant worker provisions it on its next cycle (typically minutes).

Why can't I request an "Admin" level?

Privileged roles are hidden from self-service by default. An admin can enable them per tier - they then require a global approver and a short duration.

Will a grant last forever?

No - grants are time-bound and auto-revoked at expiry. "Unlimited" only appears where an admin has allowed permanent grants for that level, and still needs the designated approver.

Can revoking break existing access I didn't request?

No. The grant worker only ever adds access; the only automatic removal is the expiry of grants GovLens itself created, by their exact assignment id. Revoking existing access always goes through mark → approve → worker.
