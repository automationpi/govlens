GovLens Operator Guide

How to deploy, configure, secure, and run GovLens for your organization. For the end-user experience (requesting/approving access), see the User Guide.

Architecture

GovLens is one container image running against your own Postgres. Inside it a small launcher supervises the web app plus the enabled background workers. Each worker uses a separate, least-privilege service principal, so no single component can both read broadly and change access.

People
Users & approversBrowser → GovLens web. Sign in via your IdP (Entra SSO).

Green = read-only · Red = delete-only · Blue = write-only · Amber = your database. The web app holds no Azure credential.

Prerequisites

  • A Postgres database and a connection string. The DB user needs create-table rights (GovLens builds its own schema on first start). Treat it as the audit store - back it up.
  • An Entra tenant and rights to create app registrations / service principals and custom roles (Application Administrator + Owner/User Access Administrator at your management-group root, or equivalent).
  • A container runtime (Docker/Podman/Kubernetes) able to run the image and mount a config file.
  • The Azure CLI (az) for the provisioning steps below.

Service principals

Create three least-privilege SPs, each assigned at your tenant/management-group root. Each can use a certificate (--create-cert) or a client secret - your choice per SP.

# set your management-group (or tenant root) scope
MG="/providers/Microsoft.Management/managementGroups/<mg-or-tenant-root>"

# 1) COLLECTOR - read-only. Reader (ARM) at the root...
az ad sp create-for-rbac --name govlens-collector --role Reader --scopes "$MG" --create-cert
#    ...plus Microsoft Graph *application* permissions (admin-consented):
#    Directory.Read.All, RoleManagement.Read.Directory, Policy.Read.All,
#    Application.Read.All, Group.Read.All, User.Read.All, Reports.Read.All …
#    (grant via `az ad app permission add` + `az ad app permission admin-consent`)

# 2) REMEDIATOR - delete-only custom role, then the SP
cat > remediator-role.json <<EOF
{ "Name":"GovLens Remediator",
  "Description":"Deletes role assignments for approved revokes.",
  "Actions":["Microsoft.Authorization/roleAssignments/read",
             "Microsoft.Authorization/roleAssignments/delete"],
  "AssignableScopes":["$MG"] }
EOF
az role definition create --role-definition remediator-role.json
az ad sp create-for-rbac --name govlens-remediator --role "GovLens Remediator" --scopes "$MG" --create-cert

# 3) GRANT - write-only custom role, then the SP
cat > grant-role.json <<EOF
{ "Name":"GovLens Access Provisioner",
  "Description":"Creates role assignments for approved grants.",
  "Actions":["Microsoft.Authorization/roleAssignments/read",
             "Microsoft.Authorization/roleAssignments/write",
             "Microsoft.Authorization/permissions/read"],
  "AssignableScopes":["$MG"] }
EOF
az role definition create --role-definition grant-role.json
az ad sp create-for-rbac --name govlens-grant --role "GovLens Access Provisioner" --scopes "$MG" --create-cert
Least privilege by design. The grant SP can write role assignments but has no delete; expiry-revocation is handled by the remediator's delete role. The permissions/read action lets the grant worker self-verify (the readiness probe) without any broader access.
Secret instead of cert: drop --create-cert to get a client secret in the command output, or run az ad app credential reset --id <app-id>. Put it in the config as secret: instead of cert:.

Note each SP's app id and keep its cert PEM / secret - you'll reference them in the config. Enable only the modules you need: a revoke-only deployment doesn't need the grant SP, and vice-versa.

Web sign-in app

Register one more app for user sign-in (OpenID Connect). This is separate from the workers and holds no Azure roles.

az ad app create --display-name govlens-web \
  --web-redirect-uris https://govlens.example.com/auth/callback \
  --enable-id-token-issuance true
az ad app credential reset --id <web-app-id>   # → client secret for the config

The redirect URI must exactly match auth.redirect_url in your config. Users just need to be able to sign in; their GovLens roles come from GovLens's own grants.

Config reference

Everything lives in one config.yaml. Copy the sample below, replace each <placeholder>, and fill in your database, auth, and service principals. Any value can use ${ENV_VAR} to read a secret from the environment instead of writing it in the file.

Sample config.yaml

# Run the whole stack from one image against your own Postgres:
#   docker run -v ./config.yaml:/etc/govlens/config.yaml -p 8080:8080 ghcr.io/automationpi/govlens

tenant:
  label: example                    # stable key shown in the UI (default: the SP tenant id)

database:
  # Bring your own Postgres; GovLens creates its own schema on first start.
  dsn: "${DATABASE_URL}"          # postgres://user:pass@host:5432/govlens?sslmode=require

server:
  addr: ":8080"

auth:
  mode: entra                       # entra | oidc | dev | off
  entra_tenant: <your-tenant-id>
  oidc_client_id: <web-app-registration-id>
  oidc_client_secret: "${OIDC_CLIENT_SECRET}"
  redirect_url: https://govlens.example.com/auth/callback
  session_secret: "${GOVLENS_SESSION_SECRET}"
  admin_emails:
    - you@example.com

# Each SP takes EITHER a certificate OR a client secret (your choice per SP).
# cert may be a file path, an inline PEM, or base64-encoded PEM.
service_principals:
  collector:                        # read-only: pulls governance data
    app_id: <collector-app-id>
    cert: /secrets/collector.pem
  remediator:                       # roleAssignments read+delete: executes revokes
    app_id: <remediator-app-id>
    secret: "${REMEDIATOR_SECRET}"
  grant:                            # roleAssignments read+write: provisions grants
    app_id: <grant-app-id>
    cert: /secrets/grant.pem
    root_scope: /providers/Microsoft.Management/managementGroups/<your-mg-root>

modules:
  collector:  { enabled: true, interval: 3600 }
  remediator: { enabled: true, execute: true, interval: 3600 }
  grant:      { enabled: true, execute: true, interval: 300 }

database.dsn (required)Your Postgres connection string. GovLens never manages a DB.
server.addrListen address (default :8080).
auth.modeentra | oidc | dev | off.
auth.entra_tenant / oidc_issuerYour tenant id (entra) or issuer URL (generic OIDC).
auth.oidc_client_id/secretThe web sign-in app's credentials.
auth.redirect_urlMust match the app registration's redirect URI.
auth.session_secretRandom string signing session cookies (required when auth is on).
auth.admin_emailsBootstrap global admins (list).

modules.{…}.enabled / execute / intervalToggle each worker; execute:false = dry-run; interval in seconds.

Secrets: cert, secret, or ${ENV}

  • Per SP: use either cert: (a file path, an inline PEM, or base64 PEM) or secret: (a client secret).
  • ${ENV} interpolation: any value may reference an environment variable, e.g. dsn: "${DATABASE_URL}" or secret: "${GRANT_SECRET}". Missing vars become empty and validation fails fast with a clear message. Mix inline and env however you like.
  • Keep certs/secrets out of the image - mount them or pass via environment. The config file itself is safe to keep in source control if all secrets are ${ENV} references.

Running it

docker run -d --name govlens \
  -v ./config.yaml:/etc/govlens/config.yaml:ro \
  -v ./secrets:/secrets:ro \                 # if you use cert file paths
  -e DATABASE_URL=… -e OIDC_CLIENT_SECRET=… -e GOVLENS_SESSION_SECRET=… \
  -e GRANT_SECRET=… \
  -p 8080:8080 \
  ghcr.io/automationpi/govlens

The launcher (govlensd) applies the schema, then starts and supervises the web app and each enabled worker, restarting any that exit. Put GovLens behind your reverse proxy / TLS terminator; the redirect URL must be the public HTTPS address.

Single component (advanced): the image also contains /web, /collect, /remediator, /grantworker, /ingest. Override the entrypoint to run just one (useful for Kubernetes, where you'd run each as its own Deployment/CronJob).

Database

  • Point database.dsn at any reachable Postgres. Schema is created/migrated automatically on start (additive, idempotent) - upgrades need no manual migration.
  • The access_requests table is your audit trail (who requested/approved/provisioned/expired). Back it up and retain per your policy.
  • Use TLS to the database (sslmode=require) in production.

First run

  1. Start with auth.admin_emails set to yourself - you become a global admin on first sign-in.
  2. Sign in, open Admin, and grant approver/admin roles to others (global or per-subscription).
  3. Let the collector run once (or wait for its interval) so the dashboard populates and the role catalog is discovered.

Enabling self-service (the gates)

The grant module is off by default and only goes live when a fail-closed checklist is green, visible on the Admin page:

  1. Capability on - global admin turns it on.
  2. Grant SP verified - enter the grant SP identity and run the readiness probe (confirms it can write role assignments and is not over-permissioned). A stale probe (24h) re-closes the module.
  3. Tier policy acknowledged - review each level's rules.
  4. Catalog - auto-discovered on collection.
  5. Subscription opt-in - each subscription admin opts their subscription in.
  6. Go live - allowed only when every gate above passes.
https://govlens.example.com/admin
Admin - the enablement gates, grant SP + readiness probe, tier policy, guardrails, and subscription opt-in.

Day-2 operations

  • Logs are line-prefixed by component ([web], [collector], [remediator], [grantworker]) - one container, greppable streams.
  • Health: GET /healthz returns 200 when the web app is up.
  • Dry-run first: set execute: false on remediator/grant to watch a full cycle make no changes, then flip to true. This is the safe way to validate before going live.
  • Intervals: tune modules.*.interval (seconds). Collector hourly, remediator hourly, grant every few minutes are sensible defaults.
  • What to watch: failed grants/revokes in the logs and in request history; the Global-Admin count guard; a grant SP that fails its periodic probe (module auto-closes).

Rotating credentials

  1. Add a new cert/secret to the SP in Entra (az ad app credential reset - keep the old one until cutover).
  2. Update the config (or the ${ENV} value) to the new credential.
  3. Restart the container; workers re-authenticate on their next cycle.
  4. Remove the old credential in Entra.

The web session signing key (auth.session_secret) can be rotated the same way - it just invalidates existing sessions (users re-sign-in).

Upgrading

  1. Pull the new image tag.
  2. Recreate the container with the same config and volumes.
  3. Schema changes apply automatically on start (additive). No manual migration.

Hardening

  • Separate credentials - never reuse one SP across modules; the read/delete/write split is the point.
  • Scope the roots tightly - assign the custom roles at the narrowest management-group/subscription scope that covers what you manage.
  • Protected roles & type policy - mark Global Administrator (and peers) non-revocable; block or require global approval for Group/Service-Principal changes.
  • TLS everywhere - HTTPS to the web app, sslmode=require to Postgres.
  • Least data - enable pseudonymize on the collector if you don't want real principal names stored.

Troubleshooting

SymptomLikely cause / fix
Container exits at start with a config errorValidation failed - the message names the missing field (e.g. database.dsn is required, or session_secret when auth is on).
Worker logs "read cert / auth failed"Wrong cert path/secret, or the ${ENV} var isn't set in the container. Certs mounted at 600 must be readable by the container user.
Grant module won't go liveA gate is red - the Go-live banner lists which (SP verification, catalog, or subscription opt-in).
Readiness probe failsThe grant SP lacks roleAssignments/write or permissions/read at the root scope - or it's over-permissioned (holds *). Use the exact custom role above.
Approved grant never provisionsGrant module in dry-run (execute:false), SP unverified this cycle, or the role is no longer requestable under policy. Check [grantworker] logs.
User can't request for themselvesTheir session predates OIDC oid capture - sign out and back in once.
Dashboard emptyNo collection has run yet, or the collector SP can't read - check [collector] logs and its ARM/Graph permissions.
